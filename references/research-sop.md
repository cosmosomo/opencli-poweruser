# 跨平台调研 SOP 与关键词策略

> 验证日期：2026-08-27
> 来源：多轮调研实践总结（小红书 SDD 253 条笔记、6 大技术渠道核验、Scopus 自动化方案、8 平台登录验证）
> 用途：指导 agent 执行跨平台议题调研的标准流程、关键词策略、平台策略、数据处理流程、工具链经验
> 适用：任何需要多平台信息采集与整合的调研任务
>
> **⚠️ 调研记录强制规范**：每次调研必须保存原始数据和过程笔记。开始前运行 `python scripts/init_research.py "议题名称"` 创建目录；搜索结果用 `Tee-Object` 存到 `raw/`；结束时花 1 分钟填 `README.md`。详见 [research-logging.md](research-logging.md)。

回顾这几轮调研（小红书 SDD 253 条笔记、6 大技术渠道核验、Scopus 自动化方案、8 平台登录验证），可复用的经验如下：
一、关键词策略
1. 一个议题 → 多关键词矩阵搜索
实际案例：SDD 调研用了 65 个关键词，分 3 批：
核心词：spec-driven development、SDD、规格驱动开发
工具词：spec-kit、openspec、speckit、specify-cli
workflow 词：ai-workflow、bmad、agent workflow
对比词：sdd vs vibe coding、spec-kit vs openspec
经验：一个议题至少拆成 4 类关键词（核心概念/工具名/工作流/对比关系），每类 5-10 个变体，批量搜索。
2. 从结果中捕获新关键词 → 递归搜索
实际案例：
搜 "AI 编程" → 结果中出现 "vibe coding" → 用 "vibe coding" 再搜 → 发现 "vibe coding 受害者" 爆款（748 赞）
搜 "SDD" → 结果中出现 "Matt Pocock"、"Kiro"、"Tessl" → 用人名/工具名再搜 → 挖到深度内容
经验：每轮搜索后，从结果标题/正文中提取 未覆盖的新词（工具名、人名、梗词、竞品名），加入下一轮关键词列表。这是发现长尾爆款和深度内容的关键。
3. 同一概念 → 不同表达交叉验证
实际案例：
"多智能体" = multi-agent = agent workflow = 多 agent 协作 = agent orchestration
"AI 编程" = vibe coding = 自然语言编程 = AI pair programming = cursor 编程
"找工作" = 秋招 = 校招 = 求职 = offer = career
经验：同一概念至少准备 中英文各 2-3 种表达，交叉搜索。不同表达覆盖的人群完全不同——"vibe coding" 覆盖玩梗/吐槽群体，"AI pair programming" 覆盖严肃技术群体。
4. 追新关键词 → 捕获趋势
实际案例：
GitHub Trending 日报级更新（今天就有 2 条新笔记）
"2026 秋招" 比 "秋招" 更精准，过滤掉往年内容
"Claude Code"、"Cursor agent"、"Codex CLI" 比 "AI 编程" 更新更前沿
经验：
加时间限定词（2026、本周、最新）
追工具名而非概念名（工具名更新更快，概念名滞后）
关注平台的"热门/最新"排序，而非只搜关键词
二、平台策略
5. 多平台交叉验证 → 信息互补
实际案例：6 大技术渠道核验发现：
GitHub Trending：项目发现（源头）
Reddit：实战经验 + 海外找工（深度讨论）
V2EX：国内程序员真实声音（吐槽/问题）
Hacker News：最前沿英文讨论（技术辩论）
知乎：深度长文分析（系统化）
掘金：中文入门教程（基础）
经验：同一个议题在不同平台搜，得到的内容类型完全不同。不要只依赖一个平台，至少用 2-3 个互补平台交叉验证。
6. 平台适配的关键词选择
实际案例：
小红书：用口语化/情绪化词（"绝了"、"踩坑"、"神器"、"后悔没早知道"）
V2EX：用技术术语/问题式（"如何评价"、"有没有人用"、"求推荐"）
Reddit：用英文+子版限定（site:reddit.com/r/LocalLLaMA）
知乎：用问题式标题（"如何评价 X"、"X 是什么体验"、"X 和 Y 哪个好"）
经验：同一个议题在不同平台要用不同的关键词风格，直接翻译关键词效果很差。
三、数据处理流程
7. 批量采集 → 去重 → 结构化 → 分类 → 总结
实际案例：SDD 调研流程：
65 个关键词批量搜索 → 原始 JSON（kw_batch1/2/3）
去重（按 note_id）→ 253 条独特笔记
读取笔记详情 → notes/ 目录
按 14 个主题分类 → 新笔记结构化整理.md
深度问题提炼 → SDD深度问题研究.md
工具专题深挖 → SpecKit专题调研.md
经验：
先批量采集再处理，不要搜一条看一条
去重是必须的，不同关键词会搜到大量重复内容
分类维度要提前设计（按主题/按工具/按观点/按情绪），不要边看边分
分层输出：原始数据 → 结构化整理 → 深度分析 → 专题深挖
8. 点赞数/时间作为质量过滤器
实际案例：
小红书：3.3 万赞的"上海最好的地方都是免费的"是超级爆款，1050 赞的"Reddit 大神找工指南"认可度高
按时间过滤：优先看 3 个月内的内容，技术领域过时很快
经验：
点赞数 > 1000 = 公认有价值
点赞数 100-1000 = 有参考价值
点赞数 < 100 = 可能是长尾/个人观点，需甄别
技术内容优先看 3 个月内的，工具/教程可放宽到 1 年
四、工具链经验
9. OpenCLI 多平台采集的标准流程
实际验证：
opencli daemon status 确认环境
opencli --profile v6pz9gjx <adapter> search "关键词" --limit N -f json 批量搜索
结果存 JSON，后续脚本处理
遇到 stale page identity → --window foreground --site-session persistent 重建会话
遇到多 profile 冲突 → 加 --profile <name>
经验：
所有命令加 -f json，便于脚本处理
limit 先小后大（先 5 条验证，再 20-50 条批量）
保守频率：同一平台 ≤ 3 次/分钟，避免风控
登录态是前提：8 个平台登录验证后才能稳定采集
10. 渲染/编码问题要提前识别
实际案例：
shturl.c 被平台渲染成 shturl.c（URL 安全代理机制的 bug）
解决：用 linux . do 或 linux 点 do 打断匹配
PowerShell 中 curl 是 Invoke-WebRequest 别名，不支持 -L 参数
经验：
域名/URL 在对话中可能被渲染转换，用代码块或反引号包裹
PowerShell 和 Linux shell 语法不同，注意别名和参数差异
中文编码问题：PowerShell 读写文件指定 UTF-8
五、可复用的调研 SOP

### ⚠️ 第 0 步：议题理解验证（强制，跳过必翻车）

**在开始任何搜索之前，必须完成以下验证，否则极有可能把"终端的 API"理解成"终端里跑的应用的 API"，给用户一堆垃圾答案。**

1. **用一句话复述对议题的理解**：写清楚"用户要的是什么"
2. **列出"不是什么"**：明确排除容易混淆的相邻概念（至少 3 条）
3. **拆出核心名词的层次**：议题中的核心名词属于哪一层？（如"终端"=终端模拟器层/PTY层/多路复用器层/应用层，必须分清）
4. **确认通用性要求**：用户要的是通用方案还是特定工具的方案？
5. **如果有任何不确定，直接问用户**，不要猜。猜错的代价是整个调研作废。

**反面案例（2026-09-14 真实翻车记录）**：
- 用户说"AI时代的终端，运行时接入终端进程的api，通用的"
- 错误理解：去调研 codex/claude code 这些 TUI 应用自己的 API
- 正确理解：终端模拟器层/PTY层的通用运行时 API，可以接入/控制任何在终端里跑的进程
- 后果：整个调研方向错误，产出垃圾答案，用户暴怒

**正确的验证应该是**：
- 复述："用户要的是能在运行时接入终端进程的通用 API，不是终端里某个应用的 API"
- 不是什么：不是 codex API、不是 claude code API、不是某个特定 TUI 应用的远程控制
- 核心名词层次："终端"=终端模拟器层（iTerm2/WezTerm/Ghostty）+ PTY层（node-pty/ConPTY）+ 多路复用器层（tmux），不是应用层
- 通用性：用户明确说了"通用的"，必须覆盖跨平台/跨模拟器的方案

### ⚠️ 第 0.5 步：平台相关性必须实际验证（禁止凭印象判定）

**禁止在没有实际搜索的情况下判定"某平台不相关"。** 必须用 1-2 个核心关键词实际搜索后，根据结果内容判断相关性。

**反面案例（2026-09-14）**：
- 判定"小红书上 AI 终端议题不相关"，直接跳过小红书用通用搜索
- 实际搜索后发现：10 条结果中 4 条直接相关，其中 herdr（183赞）是本次调研最高价值发现，直接影响技术路线决策
- 后果：差点错过核心研究对象

**验证方法**：
1. 用议题最核心的 1-2 个关键词在目标平台搜索（limit=10 即可）
2. 快速扫描标题，判断是否有 ≥2 条语义相关结果
3. 有 → 继续精读高赞内容；没有 → 记录"已验证不相关"并说明理由
4. **永远不要写"内容不相关，已排除"而没有实际搜索记录**

### ⚠️ 社媒数字不纳入技术判断

**Stars/赞数/下载量等社媒数字只能作为"关注度参考"，绝对不能作为技术判断依据。**

- 不同镜像/第三方统计本身就不一致（如"半年 2.5 万 stars"在不同来源数字不同）
- 高 stars ≠ 架构好 ≠ 适合你的需求
- 技术判断只能基于：**官方文档、源码、protocol schema、真实实测**
- 在报告中引用社媒数字时必须标注"仅作关注度参考，不构成技术判断依据"

**反面案例（2026-09-14）**：报告中写"herdr 半年 GitHub 2.5 万+ Stars"作为价值论据，用户指出这个数字不可靠且不应纳入技术判断。

### ⚠️ 发现高重合开源项目后立即转向一手资料

当调研中发现一个与用户需求高度重合的开源项目时：
1. **立即停止二手资料收集**（小红书/博客/媒体报道）
2. **直接转向一手资料**：官方文档、GitHub 源码、protocol schema、API reference
3. **做 architecture teardown**：回答具体的架构问题（PTY 谁持有、protocol 怎么设计、状态检测怎么实现等），而不是停留在"它是什么"的介绍层面
4. **判断技术路线影响**：这个项目是否改变了"自己造 vs 用现成 vs fork"的决策？

**正面案例（2026-09-14）**：发现 Herdr 后，立即从"小红书介绍"转向官方文档精读，发现它已有 socket API、observe/control 双流、controller ownership 等核心能力，直接将技术路线从"从 node-pty 重造"调整为"fork Herdr + 加 semantic adapters"或"抄其成熟设计"。

---

综合以上经验，一个标准的议题调研 SOP：
0. **议题理解验证** → 复述理解 + 列"不是什么" + 拆核心名词层次 + 确认通用性（见上方强制环节）
0.5 **平台相关性验证** → 实际搜索 1-2 个关键词，禁止凭印象判定不相关
1. 议题拆解 → 4 类关键词矩阵（核心/工具/workflow/对比）
2. 平台选择 → 2-3 个互补平台（项目源+讨论区+教程站）
3. 批量采集 → 每平台每关键词 limit=20，JSON 输出
4. 新词捕获 → 从结果中提取新词，递归搜索 2-3 轮（**升级为议题词典**：七栏骨架 + 五维评估 + AI 先验标注，见 [topic-lexicon.md](topic-lexicon.md)）
5. 去重清洗 → 按 ID 去重，过滤低质量/过时内容
6. 结构化分类 → 按预设维度分类（主题/工具/观点/情绪）
7. 分层总结 → 数据概览 → 关键发现 → 深度分析 → 行动建议
8. 经验沉淀 → 把关键词列表、平台适配、踩坑记录存入 skill/reference

## 六、舆情/风评调研专项 SOP

> 验证日期：2026-09-03
> 来源：AI 办公三产品（豆包/WorkBuddy/千问）真实风评调研实战
> 适用：任何需要"真实用户风评/口碑/吐槽"的调研任务，区别于普通信息调研

### 6.1 舆情调研与普通调研的核心区别

| 维度 | 普通信息调研 | 舆情/风评调研 |
|---|---|---|
| 目标 | 搞清楚"是什么" | 搞清楚"用户怎么看、踩了什么坑" |
| 信源要求 | 媒体/官方/教程即可 | **必须一手用户原帖**，媒体报道只能做佐证 |
| 关键词 | 中性概念词 | **负面触发词优先**（踩坑/吐槽/避雷/坑/后悔） |
| 内容处理 | 提取事实 | **正负向归类** + 槽点聚类 + 交叉验证 |
| 评论区 | 可选 | **必读**（"我也是"效应 + 替代方案） |
| 反爬 | 通用保守 | **平台差异化**（小红书严、知乎松） |
| 交付 | 事实清单 | 风评态势 + 优缺点表 + 使用技巧 |

### 6.2 舆情调研标准 SOP（8 步）

1. **议题拆解** → 确定调研对象（产品/工具/服务）+ 核心维度（价格/额度/稳定性/客服/退款）
2. **关键词矩阵** → 产品名 × 负面词（踩坑/吐槽/避雷/坑/后悔/退款/骗/智商税）× 额度词（积分/额度/会员/性价比/耐用/消耗）
3. **平台分工** → 小红书抓负面情绪 + 知乎补深度技巧 + 通用搜索补媒体佐证（黑猫投诉/什么值得买/人人都是产品经理）
4. **批量采集** → 按平台反爬节奏执行（小红书 1 关键词/30 秒/limit≤10；知乎可连续 5 次/分钟）
5. **高赞筛选** → 小红书点赞 > 100 且标题含负面词必精读；知乎 votes > 5 优先、> 50 必精读
6. **评论区挖掘** → 只对高赞笔记读评论区，找"我也是"+替代方案+争议点
7. **交叉验证** → 同一槽点在 ≥2 个平台出现 → 高置信度普遍问题；只在 1 个平台出现 → 标注"个体体验，需甄别"
8. **分层交付** → 整体态势 → 分产品详细舆情（每条带原帖链接）→ 跨产品对比表 → 优缺点表 → 使用技巧

### 6.3 平台分工与反爬节奏

| 平台 | 角色 | 关键词风格 | 反爬节奏 | 精读深度 |
|---|---|---|---|---|
| 小红书 | 负面情绪主阵地 | 口语化负面词（"踩坑""避雷""后悔"） | 严：1 关键词/30 秒/limit≤10；note/comments 可 5-10 秒连续 | 高：note + comments + download 图片 |
| 知乎 | 深度分析 + 省钱技巧 | 问题式（"如何评价 X""X 值得买吗"） | 松：可连续 5 次/分钟 | 中：answer-detail 拿全文即可 |
| 通用搜索 | 媒体佐证 + 投诉平台 | 产品名 + "投诉/评测/对比" | 无限制 | 低：摘要足够，必要时 web.fetch |

### 6.4 信源分级

| 级别 | 信源类型 | 可信度 | 用法 |
|---|---|---|---|
| S 级 | 平台一手用户原帖（带链接+互动数据） | 最高 | 核心证据，必须引用 |
| A 级 | 高赞评论区（"我也是"+具体细节） | 高 | 验证槽点普遍性 |
| B 级 | 媒体评测/深度文章（什么值得买/人人都是产品经理） | 中 | 补充数据和专业视角 |
| C 级 | 投诉平台（黑猫投诉） | 中低 | 佐证退款/客服问题，注意可能是极端个案 |
| D 级 | 官方宣传/产品页 | 低 | 仅用于核对定价和功能，不作为风评证据 |

**硬规则**：每条舆情必须携带可直接访问的原帖链接，没有链接的内容一律不能输出。二手信源必须标注"为什么找不到原帖"。

### 6.5 正负向归类方法

收集完所有舆情后，按以下维度归类：

**负向舆情聚类**（按槽点类型）：
- 额度/积分消耗类（消耗快、不透明、缩水）
- 价格/性价比类（贵、叠加购买、退款难）
- 稳定性/功能类（卡顿、报错、功能作废、切不回）
- 客服/服务类（客服差、拒绝退款、处理错误）
- 每类标注：严重程度（⭐1-5）+ 热度（出现次数/平台数）

**正向舆情聚类**（按优点类型）：
- 效果/质量类（出图好、PPT 好、代码质量高）
- 省钱/技巧类（标准模式省钱、接第三方 API、学生价）
- 生态/功能类（Skill 多、模型自由选、办公集成）
- 每类标注：代表性内容 + 互动数据

**整体判断**：负面为主 / 正面为主 / 两极分化，一句话总结。

### 6.6 实战案例：AI 办公三产品风评调研（2026-09-03）

**任务**：调研豆包专业版、WorkBuddy、千问办公三款 AI 办公产品的真实用户风评（非官方宣传），输出优缺点表和使用技巧。

**执行过程**：
1. 关键词矩阵：3 产品 × 6 负面词 × 4 额度词 = 72 组，实际执行 12 组（去重后）
2. 平台采集：
   - 小红书：6 次 search（1 关键词/30 秒）→ 13 篇精读（note + comments）→ 2 篇图片型 download
   - 知乎：3 次 search → 2 篇 answer-detail 精读（votes 7 和 53）
   - 通用搜索：补充黑猫投诉、ZAKER 实测、什么值得买、火猫评测等 8 篇二手佐证
3. 高赞筛选：小红书点赞 > 40 的笔记全部精读（最高 4058 赞 WorkBuddy Skill 教程、404 赞豆包踩坑记）
4. 评论区挖掘：精读 2 篇高赞笔记评论区，发现"接 DeepSeek API 省钱""多账号薅积分"等技巧
5. 交叉验证："积分消耗快"在小红书（WorkBuddy 141 赞 + 52 赞）和知乎（53 赞 + 7 赞）同时出现 → 高置信度普遍槽点

**关键发现**：
- 豆包：负面集中在额度缩水（7 天重置）、叠加升级、工作模式切不回、视频 720p 水印；正面在生图质量和学生价
- WorkBuddy：负面集中在积分消耗快/不透明、稳定性差、应用作废；正面在 Skill 生态和模型自由选（可接第三方 API 省钱）
- 千问：负面集中在积分猛、免费额度缩水、Token Plan 争议；正面在标准模式省钱（token 降 75-80%，实测 3 Agent 合计 28.94 积分）

**产出**：
- Markdown 调研文档（含整体态势、分产品详细舆情列表、跨产品对比表、优缺点表、使用技巧）
- 4 张 ECharts 可视化（价格对比、积分含金量、口碑倾向）
- 每条舆情带原帖链接，信源可追溯

**效率数据**：
- 总耗时：约 40 分钟（含反爬等待约 8 分钟）
- 采集：小红书 13 篇 + 知乎 2 篇 + 通用搜索 8 篇 = 23 篇信源
- 精读：15 篇一手 + 8 篇二手
- 产出：1 份完整调研文档 + 4 张图 + 优缺点表 + 使用技巧

**可复用经验**：
1. 负面词命中率比中性词高 3-5 倍，风评调研优先用负面词
2. 小红书 note/comments 反爬远低于 search，先搜完再批量精读效率最高
3. 知乎 answer-detail 一次拿完整 Markdown 正文，比小红书 note 效率高
4. 评论区是风评调研的金矿，"我也是"+替代方案价值极高
5. 同一槽点跨平台验证是区分"普遍问题"和"个体体验"的关键

## 七、议题词典：关键词的认知升级

> 详见 [topic-lexicon.md](topic-lexicon.md)。本节只放与本 SOP 的衔接点。

第一~四节的关键词策略解决"这一轮搜什么"，议题词典解决"搜到的词如何沉淀成可复用资产"。三个关键升级：

1. **从弹药到资产**：新词捕获后不是用完即弃，而是入七栏词典（核心/机制/阵营/生态/学术/社区梗/平台标签），每词做五维评估（热度/新鲜度/前沿度🔮/本质度⚙️/契合度）。
2. **AI 盲区自觉**（前沿议题第一前提）：AI 词汇知识截止于训练数据，**"AI 不认识但语料高频"是最强前沿信号**。开工先声明盲区，词典每词标 `AI先验`，强制跑第二轮反查。只做一轮 = 只拿到 AI 已知的世界。
3. **配额分配联动反爬**：🔥核心词走 search（贵，30秒/词，第6词即限流）；❄️外层词走 note 精读（便宜，7秒/篇，51篇连打零风控）。先攒 search 列表再批量 note 精读。

工具：`python scripts/lexicon_scan.py {tags|freq|tier|inventory} <调研目录> [词表]`。

## 八、推理决策树强制规范（2026-09-12 新增）

> **硬规则：每次调研必须产出 `output/推理决策树_YYYY-MM-DD.md`，与主报告并列。**
> 来源：token管饱调研实战（三路并行采集+用户约束变更+国内追加深挖），用户明确要求"禁止凭印象代写，必须基于真实执行经验"。

### 8.1 为什么必须有推理决策树

1. **可追溯**：每个结论都能回溯到"为什么选这个平台/关键词/来源"，不是黑箱
2. **可复用**：模板化后下次调研直接填空，避免重复踩坑（如linux.do login过期、v2ex无search、302.AI噪声）
3. **可审计**：失败项和遗留问题明确记录，不掩盖
4. **可迭代**：用户约束变更时，能快速定位影响范围并调整推荐

### 8.2 推理决策树的 8 个节点（必须全部填写）

| 节点 | 内容 | 要求 |
|---|---|---|
| 0. 调研目标定义 | 用户原始需求、核心语义解析、已用基线、输出定义 | 必须写清"不是什么"以限定范围 |
| 1. 平台选择决策 | 选了哪些平台、为什么、为什么不选其他 | 每个平台有预期价值和风险 |
| 2. 关键词生成与迭代 | 关键词矩阵、第一批词、迭代规则、收敛标准 | 必须说明何时换词/何时扩展/何时停 |
| 3. 命中/未命中分支 | 每个关键词的实际命中数、挖到什么、后续动作 | **基于真实执行记录，禁止凭印象** |
| 4. 风控与绕行决策 | 遇到的问题、尝试的解法、最终方案 | 失败的尝试也要记录 |
| 5. 交叉验证决策 | 每个关键结论的多源对比、是否一致、可信度 | 多源不一致时全部列出，不强行统一 |
| 6. 结论可信度分级 | ⭐⭐⭐⭐⭐已查证 / ⭐⭐⭐⭐基本可信 / ⭐⭐⭐待核实 / ⭐⭐低可信 | 每条结论标注等级 |
| 7. 用户约束变更处理 | 变更内容、影响分析、调整决策 | 用户中途改需求时必须记录 |
| 8. 失败项与遗留问题 | 未完成项、原因、补救/后续 | 不掩盖失败 |

### 8.3 关键词库实证规范

- 关键词库必须基于子代理**真实执行轨迹**（raw/ 原始JSON实核 + 实际调用记录）
- 每个关键词标注【实证有效/实证低效/实证无效/被拦截/未验证】及实际命中数
- 禁止凭印象或领域知识代写"已验证"关键词
- 候选扩展词（未验证的）放在附录，不与实证词混排

### 8.4 生态发现先行规范（全覆盖评估类调研）

当任务要求"全覆盖评估"时：
1. **清单降级为种子线索**，不作为覆盖底线
2. **前置步骤：生态发现**——先用真实搜索发现当前生态全貌（应用商店榜单、媒体报道、社区讨论、官方页）
3. **评估范围以发现结果为准**，种子清单仅作对照，遗漏项以发现为准补充
4. 报告开头必须有【生态发现章节】，标注哪些是种子清单里没有、由真实搜索新增的方案

### 8.5 模板位置

推理决策树空表模板见任一调研项目的 `output/推理决策树_*.md` 第二部分，可直接复制使用。
