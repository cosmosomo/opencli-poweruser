## 可用命令（L0 实录，13 条）

### [read] 只读（安全）

| 命令 | 用途 |
|---|---|
| `whoami` | 当前登录账号 |
| `me` | 个人资料（余额 / 未读提醒） |
| `hot` | 热门话题 |
| `latest` | 最新话题 |
| `topic <id>` | 主题详情 + 回复 |
| `replies <id>` | 主题回复列表 |
| `node <name>` | 节点话题列表 |
| `nodes` | 所有节点列表 |
| `member <username>` | 用户资料 |
| `user <username>` | 用户发帖列表 |
| `notifications` | 提醒（回复 / @） |

### [write] 写操作（⚠️ 需用户明确授权）

| 命令 | 用途 |
|---|---|
| **`daily`** | **每日签到并领取铜币** —— 会改动账号状态 |
| `login` | 打开登录页并等待认证 |

## ⚠️ `daily` 是写操作，不要顺手跑

`daily`（签到）看起来人畜无害，但它**在用户账号上产生真实动作**，属安全铁律 #2 管辖：
执行前必须告知用户并获授权，禁止自动执行。
（2026-08-27 的旧记录把它和只读命令混在一张表里，未标写属性——已在本卡纠正。）

## ⚠️ 没有 `search` 命令

V2EX 适配器**不提供全文搜索**。定位内容只能靠：

```bash
opencli v2ex node programmer --limit 20 -f json   # 按节点泛读
opencli v2ex hot -f json                           # 热门
opencli v2ex latest -f json                        # 最新
```

**采集策略链**：按节点泛读（jobs / programmer / share / work）→ 人工筛标题 → `topic` 精读。

→ 这决定了 V2EX 的用法是**节点泛读 + 人工筛**，不是关键词精确检索。
想按词找，只能先 `nodes` 定节点，再在节点内翻。
（"假设别人有的它也有"的典型反例，见 [channel-probing.md](channel-probing.md) §一）

### 节点定位

| 节点 | 内容 | 求职相关度 |
|---|---|---|
| `jobs` | 招聘信息，以社招远程岗为主 | 中（**校招密度低**） |
| `programmer` | 程序员技术讨论 | 中（AI / Agent 讨论活跃） |
| `work` | 工作相关 | 中 |
| `share` | 分享创造 | 低 |
| `career` / `devops` / `ai` / `python` / `nodejs` / `golang` | 垂直方向 | 视议题而定 |

> 2026-09-17 实测 `jobs` 节点：确有远程岗（测试 15-22K、量化 30-50K、AI 产品总监上海），
> 但**校招密度低**，求职场景下建议降级为**巡检渠道**而非主力采集渠道。

## 反爬与节奏

**风险低**——V2EX 对读取接口限流宽松，未遇严重风控。保守低频即可。

## 能力边界：取得到什么 / 取不到什么

| ✅ 取得到 | 说明 |
|---|---|
| 按**节点**分区的话题列表 | `node <name>`；`nodes` 可列全部节点 |
| 全站热门 / 最新 | `hot` / `latest` |
| 主题详情 + 回复 | `topic <id>` / `replies <id>` |
| 用户维度 | `member`（资料）/ `user`（发帖列表） |

| ❌ 取不到 | 影响 |
|---|---|
| **全文检索**（无 `search` 命令） | **这是本适配器最硬的约束**：只能"按节点泛读 + 人工筛"，不能按词定位。任何"想找关于 X 的帖子"的需求，在本渠道都得先翻译成"去哪个节点翻" |
| 图文 / 富媒体 | 纯文本帖 + 回复 |
