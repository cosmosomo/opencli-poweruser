# 调研脚本可复用模式与参数化设计规范

> 验证日期：2026-08-27
> 分析对象：xhs_search 项目（~15 个 PS1，小红书 SDD 调研，253 条笔记）
> 用途：指导 agent 理解调研脚本的可复用模式、现有脚本的问题、以及参数化脚本的设计规范
> 配套：references/research-sop.md（调研 SOP 与关键词策略）

---

## 一、脚本体系分层（参考模型）

一个完整的多关键词调研脚本体系分三层：

| 层级 | 核心功能 | 典型操作 |
|---|---|---|
| **搜索层** | 关键词矩阵批量搜索 | 关键词列表 → 自动编号 → 逐个搜索 → 间隔限流 → JSON 存储 + 映射表 |
| **读取层** | 笔记/帖子详情批量抓取 | 按 rank/URL 定位 → 调 detail/note 命令 → 清洗存储 → 间隔限流 |
| **处理层** | 去重、分类、报告生成 | 多批结果去重合并 → 新内容识别 → 关键词规则自动分类 → Markdown 报告生成 |

---

## 二、可复用的代码模式（7 种）

这些模式是从 xhs_search 脚本中提炼的，换议题/换平台时可直接复用：

### 1. 关键词矩阵批量搜索
关键词列表 → 自动编号（kw01, kw02...）→ 逐个调用搜索 → 间隔限流（6-8 秒）→ 结果存 JSON + kw_map.json（编号→关键词映射）

### 2. JSON 清洗
OpenCLI 输出常混有 `Update available`、`RemoteException`、`npm install` 等噪音行。清洗方法：提取第一个 `[` 到最后一个 `]` 之间的内容，再 `ConvertFrom-Json`。

### 3. 多批去重合并
按标题去重，同一笔记取最高赞，记录出现过的关键词标签。适用于多批关键词搜索结果的合并。

### 4. 新内容识别
对比已读内容的标题集合，筛选未读内容，按点赞/热度排序。适用于增量调研。

### 5. 关键词规则自动分类
预设 N 个主题 × 每个主题的关键词列表，按顺序匹配（先匹配的优先），生成目录总览表 + 分类详情表。末尾设"其他"兜底。

### 6. 详情批量读取
从搜索结果中按 rank 或 URL 定位目标 → 调用 detail/note 命令 → 清洗后存储 → 间隔限流。

### 7. Markdown 报告生成
用 StringBuilder 拼接：目录总览表（主题/条数/最高热度）+ 分类详情表（序号/标题/作者/热度/时间/链接）+ 全文汇总。

## 三、现有脚本的问题（硬编码清单）

xhs_search 的 15 个脚本存在以下阻碍复用的问题，**重写参数化脚本时必须避免**：

| 问题 | 具体表现 | 影响 |
|---|---|---|
| 硬编码路径 | 所有脚本写死项目目录 | 换项目/目录就要改代码 |
| 硬编码关键词 | 关键词列表直接写在脚本里 | 换议题就要复制改脚本 |
| 硬编码分类规则 | 主题+关键词写死在处理脚本里 | 换议题分类规则全废 |
| 硬编码目标列表 | 读取脚本写死文件名+rank | 每次精读都要手动改 |
| 单平台绑定 | 全部调用 `opencli xiaohongshu` | 不能直接用于 Reddit/V2EX/知乎 |
| 无参数化 | 不能通过命令行指定关键词/平台/输出目录/limit | 灵活性差 |
| 无错误处理 | 搜索失败/JSON 解析失败直接跳过，无日志 | 不知道丢了多少数据 |
| 无进度追踪 | 只有 Write-Output 打印，无统计 | 无法评估覆盖率 |
| 无配置文件 | 关键词、分类规则、平台选择都在代码里 | 配置和逻辑耦合 |

## 四、参数化脚本设计规范

如果重写参数化核心脚本，遵循以下原则：

### 4.1 推荐的 2 个核心脚本

| 脚本 | 功能 | 关键参数 |
|---|---|---|
| `batch-search.ps1` | 多关键词多平台批量搜索 | `-Keywords @(...)`、`-Platform <name>`、`-OutDir <dir>`、`-Limit <n>` |
| `dedupe-and-classify.ps1` | 多批结果去重 + 关键词规则分类 + Markdown 生成 | `-InputDir <dir>`、`-Rules @{主题=关键词列表}`、`-OutFile <file>` |

### 4.2 设计原则

1. **路径全部参数化**，不硬编码任何项目目录
2. **平台通过参数选择**，内部映射到 opencli 命令（`xiaohongshu` / `reddit` / `v2ex` / `zhihu` 等）
3. **分类规则通过 hashtable 参数传入**，不写死在脚本里
4. **加基本错误处理和进度统计**：搜索失败计数、JSON 解析失败日志、最终覆盖率报告
5. **UTF-8 无 BOM 输出**：用 `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`
6. **参数控制在 5 个以内**，提供合理默认值，避免参数化过度导致 agent 不会调
7. **平台字段映射**：不同平台输出字段不同（小红书 likes，Reddit score），内部统一成 `title/author/popularity/url/published`

## 五、核心判断

**方法论价值高，代码复用价值低。**

这些脚本真正有价值的不是代码本身，而是它们体现的"多关键词矩阵调研"方法论——这正是 skill 应该沉淀的知识（见 research-sop.md）。代码因为硬编码太多，其他 agent 拿到也不能直接用。

**正确做法**：提炼方法论写进 reference（已完成，research-sop.md），同时可选提供 1-2 个参数化核心脚本作为工具，而不是把 15 个硬编码脚本原封不动塞进去。

**不建议**把现有硬编码脚本原封不动塞进 skill——它们只对单一议题有用，换议题就要全改，沉淀价值低。
