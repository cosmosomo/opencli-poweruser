# 渠道研发与探活 SOP

> 建立日期：2026-09-17
> 用途：把"开一个新渠道"从每次重新摸索，变成一条固定流水线。
> 为什么单列：探活是**每接一个平台都要重复做**的动作，但经验此前散落在 pitfalls、verified-platforms、
> 各 adapter 卡里，导致同一类坑被反复踩（whoami 误报已在 4 个平台各踩一次）。
> 配套：[new-site-exploration.md](new-site-exploration.md)（要不要写适配器）、
> [data-quality-checklist.md](data-quality-checklist.md)（数据对不对）、[pitfalls.md](pitfalls.md)

---

## 〇、渠道研发五步

```
① 盘点能力      opencli --help 找适配器 → opencli <a> --help 看真实命令清单
       ↓
② 能力边界判定   这些命令能不能满足需求？——⚠️ 必须在鉴权调试之前做
       ↓
③ 探活阶梯      L0 本地 → L1 免登录 → L2 轻量数据命令 → L3 cookie 层 → L4 页面层
       ↓
④ 数据质量      非空 → 肉眼/交叉比对 → 单位量级 → 字段语义（见 data-quality-checklist）
       ↓
⑤ 定级落卡      🟢/🟡/⛔/🔴/⚪ 写进速查表 + adapter-<name>.md
```

---

## 一、铁律 1：能力边界判定必须在鉴权调试之前

**先问"它能给我什么"，再问"怎么登进去"。** 顺序反了会把大量时间花在一个即使打通也没用的通道上。

**判据**：把 `opencli <adapter> --help` 的命令清单逐条对照需求，特别注意**同名不同向**的命令：

| 陷阱 | 实例 |
|---|---|
| **B 端 / C 端搞反** | 脉脉 `search-talents` 是**招聘方搜候选人**（`/ent/talents/`），不是求职者搜岗位/看内容。即使鉴权完美，对求职侧依然零价值 |
| 命令名相同、数据源不同 | 小红书 `whoami` 走 `creator.xiaohongshu.com`，与 `www` 浏览态是两套 cookie |
| 假设"别人有的它也有" | v2ex **没有 `search`**，只能靠 `node`/`hot`/`latest` 泛读 |
| 名字像但完全无关 | `jianyu`=剑鱼标讯（招标）、`powerchina`=电建采购公告，都不是求职 |

**动作**：能力不匹配 → 直接判 `⚠️ 能力不匹配` 并写明原因，**不要进入探活**；
真正需要的能力若站点本身有、只是适配器没覆盖 → 转 [new-site-exploration.md](new-site-exploration.md) 评估自建。

## 二、铁律 2：不要用 `whoami` 探活

> **已确认 4 个独立误报案例，全部是"浏览器实际已登录、whoami 报未登录"。**

| 平台 | whoami 依赖的锚点 | 失效原因 |
|---|---|---|
| linux.do | 页面 meta 标签 `current-user-username` | 该标签在当前页面不存在 |
| 小红书 | `creator.xiaohongshu.com` 登录态 | 与 `www` 浏览态是**两套 cookie**，创作平台掉登录不影响采集 |
| 脉脉 | 内联脚本 `userObj = JSON.parse('{...}')` | 站点改版后该脚本不再注入 |
| 一亩三分地 | `#um` / `.vwmy a` / `a.username` | 站点从 Discuz 迁到新版 `/home`，旧锚点全废 |

**根因规律**：`whoami` 为了"轻"，往往吊死在**一个脆弱的单点锚点**上（meta 标签 / 内联脚本 / 特定 DOM id / 另一个子域）。
而真正的数据命令走的是站点主链路，**主链路的稳定性远高于身份探针**。

**推论**：`whoami` 报 `AUTH_REQUIRED` 时，**它证明不了你没登录**，只证明那个锚点没找到。

## 三、探活阶梯（按成本与风险从低到高）

**用最低一级能得出结论就停，不要一上来打最贵的命令。**

| 级别 | 做什么 | 成本/风险 | 能回答什么 |
|---|---|---|---|
| **L0 本地** | `opencli <a> --help`（可加 `-f yaml` 看参数与 `browser:` 标志） | 零，不联网 | 命令是否存在、要不要浏览器、有哪些筛选参数 |
| **L1 免登录通道** | 跑 `browser:false` 且无需登录的命令 | 零风险 | 通道本身通不通（牛客 `jobs`/`trending` 实测 daemon 未运行也能跑） |
| **L2 最轻数据命令** | `search --limit 1` / `feed --limit 3` | 低 | **登录态 + 数据可得性**（这是判定"能不能用"的正解） |
| **L3 cookie 层** | `browser <sess> eval 'document.cookie'` | 低 | L2 失败时区分"没登录"还是"探针坏了"。看关键 cookie 是否存在（如 `u`/`session`/`_auth`）。⚠️ HttpOnly 看不到，需走 CDP |
| **L4 页面层** | `browser open <url>` + `extract` / 找"退出"文案 | 中（会导航） | 站点是否改版、登录墙是否解除、内容长什么样 |

**注意**：L4 会导航页面，**人工登录期间禁止执行**（见 [pitfalls.md](pitfalls.md) §14）。

## 四、四种失败的鉴别

探活失败不等于不可用。先分清是哪一种，再决定动作：

| 现象 | 是哪种 | 判据 | 动作 |
|---|---|---|---|
| `AUTH_REQUIRED` + 数据命令也空 | **真未登录** | L3 看不到关键 cookie | 让用户在 Chrome 里登录 |
| `AUTH_REQUIRED` 但数据命令正常 | **探针失效（误报）** | L3 能看到关键 cookie / 页面有"退出" | 忽略 whoami，直接用数据命令；记进 adapter 卡 |
| 命令报错提到的选择器/端点在页面上找不到 | **站点改版** | L4 看到新版 UI / 旧 URL 被重定向 | 查 `browser analyze`，评估自建或降级浏览器通道 |
| 前几次正常、之后突然空返回 | **限流** | 冷却后恢复；或有显式 busy 页 | 降频、换平台，见 [anti-bot-notes.md](anti-bot-notes.md) |

**通用纪律**：连续 2 次异常立即停手，不要连打——连打只会拉长冷却，还可能把"限流"升级成"封号"。

## 五、定级与落卡

探活结束必须产出一个**状态位**，写进 SKILL.md 速查表；细节进 `adapter-<name>.md`。

| 级别 | 含义 | 典型 |
|---|---|---|
| 🟢 **可用** | 命令通、数据对、无需特殊处理 | 51job（免登录）、牛客公共通道 |
| 🟡 **半残** | 能跑但有字段缺失/需人工介入 | Indeed（title 全空 + Cloudflare 盾） |
| ⛔ **需登录** | 通道本身没问题，缺登录态 | LinkedIn、一亩三分地 |
| 🔴 **禁区** | 技术上可能能跑，但**账号/合规风险不接受** | BOSS 直聘（真实投递账号曾被限 24h） |
| ⚠️ **能力不匹配** | 命令方向不对，鉴权再好也没用 | 脉脉 `search-talents`（B 端搜人） |
| ⚪ **无适配器** | 需评估自建 | 转 new-site-exploration.md |

> 🔴 与 🟡 的区别是**风险归属**：🟡 是数据质量问题，🔴 是账号/人身风险问题。
> **"技术上能跑"从来不是使用它的理由**——两者是独立判断，风险优先。

## 六、检查清单（每开一个新渠道走一遍）

- [ ] 跑过 `opencli <a> --help` 了吗？（别假设它有 search/comments）
- [ ] **能力边界判定做在鉴权之前了吗？** 命令方向对不对（B 端 vs C 端）？
- [ ] 探活用的是数据命令，不是 `whoami` 吗？
- [ ] whoami 报未登录时，用 L3/L4 独立验证过再下结论了吗？
- [ ] 失败归类清楚了吗（未登录 / 探针失效 / 改版 / 限流）？
- [ ] 数据质量过了 [data-quality-checklist.md](data-quality-checklist.md) 的 5 步没有？
- [ ] 产出状态位并写进速查表了吗？细节进 `adapter-<name>.md` 了吗？
- [ ] 如果判定为 🔴 禁区，**写清楚风险归属**（是账号还是合规），避免后人只看到"技术可用"就去用
